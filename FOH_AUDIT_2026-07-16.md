- Numbers are computed, not hardcoded — totals, tips, comps all derived from entered fields ([foh-closing.js:116-126](foh-diagnostic/foh-closing.js:116)); the only estimate (48/51/1% F&B split when left blank) is explicitly disclosed on screen ([foh-closing.js:122](foh-diagnostic/foh-closing.js:122)).
- Fails safe on network/API loss throughout (SevenRooms covers fetch, history load, AI insights — [foh-closing.js:41-45](foh-diagnostic/foh-closing.js:41), [foh-closing.js:219](foh-diagnostic/foh-closing.js:219), [foh-ops.js:115-141](foh-diagnostic/foh-ops.js:115)).

Neither drops real data — `clOpen(date)` for a specific date bypasses the cap entirely ([foh-closing.js:22](foh-diagnostic/foh-closing.js:22)).
- Business-date rule verified still correct: pre-06:00 Dubai time files under the previous night, via `common.js:35-37`, unit-tested at [tests.js:32-38](foh-diagnostic/tests.js:32).

### Revenue — **WORKING**
Manager's goal: replace the Excel Daily Budget sheet, and let an AI "Analyst" explain trends without it inventing numbers. Verified:
- The "AI does zero arithmetic" rule is genuinely enforced structurally, not just by prompt: the edge function `functions/revenue-assistant/index.ts:19-56` is a dumb Claude proxy with no business logic; all math is pure client functions (`revStats` [foh-revenue.js:445-472](foh-diagnostic/foh-revenue.js:445), `revScenario` [foh-revenue.js:188-234](foh-diagnostic/foh-revenue.js:188)); the system prompt states "HARD RULE — ZERO ARITHMETIC… every figure must appear VERBATIM" ([foh-revenue.js:580](foh-diagnostic/foh-revenue.js:580)); the model is fed only pre-rounded tool results, never raw rows.
- Persistence: `rev_daily` upsert on `service_date` ([foh-revenue.js:305-335](foh-diagnostic/foh-revenue.js:305)), `rev_targets` upsert on `period` ([foh-revenue.js:242-255](foh-diagnostic/foh-revenue.js:242)); both revert the in-memory value and alert on failure rather than showing a false "saved" state ([foh-revenue.js:249,327](foh-diagnostic/foh-revenue.js:249)).
- The historical PostgREST 1000-row cap (which would silently truncate the newest month first, since `rev_daily` is ordered ascending) is explicitly paginated around in `revFetchAllDaily()` ([foh-revenue.js:17-27](foh-diagnostic/foh-revenue.js:17)).
- AI-proposed changes (`propose_change`) are never auto-applied — require an explicit user click via `revApprove` ([foh-revenue.js:538-544](foh-diagnostic/foh-revenue.js:538)).
- Caveat (unverified, out of this file's scope): the spec describes `closing_reports` as the primary entry point that rolls into `rev_daily` — confirmed true from the Closing Report audit above, so this is resolved, not a real gap.
- Minor assumption to flag: an un-split day attributes its whole area total to "Dinner" by convention ([foh-revenue.js:124-135,274](foh-diagnostic/foh-revenue.js:124)) — correct today, would mislabel if lunch is ever open on such a day.

- Email/print/Excel are real, not stubs: Excel via SheetJS ([stock-take.js:750-761](foh-diagnostic/stock-take.js:750)), email via a live Resend-calling edge function ([functions/send-stock-take/index.ts:48-52](foh-diagnostic/functions/send-stock-take/index.ts:48)).

RLS is fully open (`allow all` to anon, [stock-take-schema.sql:89-99](foh-diagnostic/stock-take-schema.sql:89)) — a deliberate beta tradeoff, not an oversight, per the SQL's own comment.

  - Every gap it finds is presented in a dialog whose confirm button is literally labelled **"Send anyway"** ([foh-privateevents.js:1549-1553](foh-diagnostic/foh-privateevents.js:1549)) — dismissible, not a hard stop.

## 3. Fonts + visual system

**`colors.md` verbatim** ([colors.md:1-9](foh-diagnostic/colors.md:1)):
```
Roberto's Brand Colors (from Kitchen App):
- Sabbia Chiara (background): #F5F0E8 — warm sand/cream
- Vino Amarena (headers/accent): #6B1F2A — deep wine red
- Text primary: #2C1810 — dark brown
- Text secondary: #8B7355 — warm taupe
- Gold accent: #C9A84C
- White: #FFFFFF
- Light border: rgba(107,31,42,0.15)
```

**This documented spec does not match the true brand guideline** (Vino Amarena #400207, Sabbia #E8D9C7). `colors.md` appears to document an earlier, lighter palette carried over from the Kitchen app, and its own font line ("Georgia serif") matches neither the true brand fonts (Bodoni Moda/Forum) nor what the code actually loads.

## 4. Navigation model

Two-tier, confirmed by reading the actual router:
1. **Public home** (no login) — 3 boxes: **Schedule** (`fohTab('schedule')`), **Management** (`fohTab('manager')`), **Checklists** (`openChecklists()`) — [index.html:2259-2278](foh-diagnostic/index.html:2259). A hardcoded link jumps to the separate Kitchen app ([index.html:2284](foh-diagnostic/index.html:2284)).
2. **Management → login → Hub** — after `sb.auth` sign-in, the Manager landing shows up to 7 module cards, grouped "Tonight & every day" / "Business" / "Guests" ([index.html:2332-2411](foh-diagnostic/index.html:2332)), each hidden per-user by `applyFohAccess()` ([index.html:2799-2825](foh-diagnostic/index.html:2799)).
3. **`enterApp(module)`** ([index.html:3834-3858](foh-diagnostic/index.html:3834)) re-checks the access gate even if a tile was somehow clicked, marks the module's "NEW" badge seen, and lands the user either straight in that module (Revenue/Operations/Stocktake/Admin/PrivateEvents/Reviews) or, for Events, preserves whatever event-family tab they were last on.
4. **`switchTab(tab)`** ([index.html:3867-3874](foh-diagnostic/index.html:3867)) is the single re-render choke point: resolves aliases (`leaders`→`dashboard`, `listening`/`jazz`→ that week's event tab), re-applies the access gate, then re-renders nav + main.
5. Within Events, sub-tabs are per-activation (Leaders + one tab per live event, [index.html:2741-2752](foh-diagnostic/index.html:2741)); every other module is a single page reached only from the hub — no cross-module nav bar.
6. **Unsaved-work-on-back-navigation**: not centrally handled — each module's own modals must revert/persist on their own (verified case-by-case above: Schedule/Checklists/Revenue/Closing Report all explicitly revert-on-failure; the Events wizard is multi-step but each step auto-saves as you go, [foh-privateevents.js:1419-1477](foh-diagnostic/foh-privateevents.js:1419)).
7. Session restore (`restoreSession()`, [index.html:3921-3939](foh-diagnostic/index.html:3921)) reopens the last tab from `localStorage` on reload — so an in-progress session survives a refresh, but there is no app-level "you have unsaved changes" interstitial.

## 6. Improvements — ranked

1. **Close the guest-send gate for date/guest-count, and make it a real block, not "Send anyway."**
   Evidence: [foh-privateevents.js:1526-1554](foh-diagnostic/foh-privateevents.js:1526) never checks `e.event_date`/`e.guests`, and every gap it does find is dismissible.
   Consequence: a client can be sent (and can sign) an agreement for an event with no confirmed date or headcount — the exact costly mistake the guided wizard already prevents one path but not the direct-edit path. Guest-facing sends are also central to the Valentina/Non-negotiables rules — this is the single highest-leverage fix in the app.
   Fix: add date/guest-count to `peSendChecks`, and make missing-price / missing-date / missing-guests hard blocks (return, no confirm) the same way `peSendPaymentLink` already hard-blocks a missing `payment_link`/`contact_email` ([foh-privateevents.js:2564-2565](foh-diagnostic/foh-privateevents.js:2564)) — preserves the existing softer warnings (allergens, split-gap, double-booking) as overridable, since those are judgment calls, not missing-data crashes.

2. **Confirm (in the Supabase dashboard) whether `weeks-add-fnb-comp-columns.sql` has actually been run against the live DB.**
   Evidence: [weeks-add-fnb-comp-columns.sql:1-9](foh-diagnostic/weeks-add-fnb-comp-columns.sql:1) states plainly that until it runs, every "Enter Results" save 400s — not just the new fields, since `saveActuals()` sends all fields in one `.update()` ([foh-events.js:2020-2032](foh-diagnostic/foh-events.js:2020)).
   Consequence: if unrun, Activations performance tracking (the data the exec dashboard is meant to build on next) has been silently failing to save entirely.
   Fix: five-minute check, no code change needed if already run.

3. **Verify the Guest Reviews cron actually exists.**
   Evidence: no `cron.schedule` for `google-reviews` anywhere in this repo; the digest recipients are hardcoded ([supabase/functions/google-reviews/index.ts:169](foh-diagnostic/supabase/functions/google-reviews/index.ts:169)); first scheduled send is Monday 20 Jul per your own notes.
   Consequence: if the cron isn't actually wired (e.g. only exists as an idea, not a Supabase-dashboard job), the digest simply never fires — safe failure direction, but worth confirming before you're expecting it Monday.
   Fix: check the Supabase dashboard's Cron Jobs page directly (same place `send-roster`'s source already lives per existing project notes).

4. **Fix `openWeekReport()`'s stale-data misread for older activation weeks.**
   Evidence: [foh-events.js:985-1030](foh-diagnostic/foh-events.js:985) never calls `ensureWeekLoaded()`, so `state.tasks[w.id]||[]` silently shows "0 tasks / AED 0" for any week older than the 60-day active window — indistinguishable from a genuinely empty night.
   Consequence: the one screen built to compare activation nights over time misrepresents older history.
   Fix: call `ensureWeekLoaded(weekId)` for each week before building the report, same pattern already used in `renderEventPage`.

5. **Unify the color/font system — pick one brand spec and update `colors.md`.**
   Evidence: three coexisting palettes ([colors.md:1-9](foh-diagnostic/colors.md:1) vs. `#400207`/`#E8D9C7` hardcoded in Admin, [index.html:3089-3385](foh-diagnostic/index.html:3089), vs. guest pages), and Bodoni Moda/Forum never loaded anywhere.
   Consequence: no client-facing visual inconsistency has caused a functional bug yet, but the brand drift is real and will compound as more screens are built against whichever palette a given contributor happened to copy.
   Fix: decide the one true palette/fonts, update `colors.md` to match, then a mechanical pass to replace hardcoded hex with the CSS vars (already the dominant pattern — 499 var usages vs. 71 hardcoded).

6. **Give Stock Take's plain quantity box a visible ✓ on save.**
   Evidence: [stock-take.js:288-299](foh-diagnostic/stock-take.js:288) — success has no toast, only the number itself changing.
   Consequence: minor UX gap, real only if two people use that box (rather than "+add") concurrently on the same item — low-frequency but a genuine miss against the Valentina rule.
   Fix: one-line `toast('Saved ✓')` alongside the existing failure toast.

None of the above requires removing any existing working action — all are additive gates or fixes around the current flows, consistent with "an audit never justifies deleting a working real-world action."

## 7. Scores (1–10)

- **Reliability: 8/10** — every save path across every module checked either persists correctly or fails visibly with a specific message; the one real save-failure risk found (`weeks-add-fnb-comp-columns.sql`) is a DB-migration state question, not a code defect, and the app's own row-cap awareness (Stock Take, Schedule, Revenue) is unusually thorough for a beta app.
- **Data accuracy: 8/10** — the "app computes, AI narrates" rule is genuinely enforced end-to-end in Revenue (verified at the edge-function level, not just the prompt), and Activations performance figures are honestly hand-transcribed with documented caveats; docked for the `openWeekReport()` stale-zero bug and the Guest Reviews cron being unverifiable from code.
- **Ease of use: 7/10** — nav model is simple and consistent (single hub, no cross-module tab clutter), confirmations are named-and-consequenced in text; docked because destructive confirms use unstyled `confirm()` rather than the branded modal, and disabled buttons never explain *why*.
- **Consistency: 5/10** — three coexisting color systems and three coexisting font stacks in one repo, plus a misnamed `.btn-gold`, is the clearest inconsistency found in this audit; functional patterns (upsert+toast+revert-on-failure) are, by contrast, very consistent module to module.
- **Scalability: 7/10** — the 1000-row PostgREST cap is explicitly and correctly paginated around in Revenue/Stock Take/Schedule; a few smaller un-labelled caps remain (Closing Report's 30-row recent list, Activations' 60-task leader list, `event_log`'s 50-row cap) but none currently risk real data loss at this restaurant's actual volume.
- **Overall: 7/10** — a genuinely well-engineered, unusually self-aware codebase (its own comments repeatedly document and defend against past bugs), let down by one real guest-facing safety gap (the send-gate) and a visible brand-consistency drift that's cosmetic today but will get more expensive to unify the longer it's left.
